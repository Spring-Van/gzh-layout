# 2026-09-14 工作日志

## 改造：批量生成提示词弹窗 —— 成功自动确认 + 失败可从输入框当前内容重试

### 用户三条要求
1. 失败后只能在底部看到「保存结果」、看不到「重新生成」→ 要求把重试按钮放到明显位置；
2. **不管是开始生成还是重试，都以上面输入框内的提示词发送**（失败了改过提示词就按改后的发，输入框里是啥就发啥，一次性/逐条同理）；
3. 请求成功后**默认确认，不要二次确认**；觉得不好用户自己再改或对单条重新请求 AI（每个资产本身都有单独「AI 重写」功能）。

### 改前的逻辑（审查结论）
- 底部只有「关闭 / 保存结果」两个按钮；**重试入口藏在进度区**（条件 `!running && failedCount`），跑完且有失败才出现，很不显眼。
- **一次性发送的重试有 bug**：`retryFailedPrompts` 用的是 `batchContext.prompt`（首次发送时的文本），用户事后改了顶部输入框**无效**。
- 逐条发送：每条成功即 `emit('update:asset')` 落库；但用户改过的文本要等点「保存结果」才覆盖。一次性发送：成功后**不落库**，必须点「保存结果」。

### 代码改动

### 关键设计判断
- **「输入框内容即发送内容」的统一原则**：重试一律由弹窗把当前文本回传，父组件不再自己拼装/记忆原文。这条同时覆盖逐条与一次性两条路径。
- **一次性发送的重试只能整批重发**（单次请求的特性决定，无法只重跑某几条）——已在 UI 文案明确：`修改上方提示词后点「重新生成失败项」，将整批按当前内容重发`。
- **自动确认用 `silent` 保存**：既落库又不关弹窗，用户可继续改（点「保存修改」）或对单条走「AI 重写」，符合用户「不用二次确认」的要求。

## 排查：「OpenAI API 格式」测试连接报「返回数据格式异常，无有效内容」（规划，未改码）

**现象**：用户用 `https://apihub.agnes-ai.com/v1` + `agnes-2.5-flash` 测试，报格式异常；同一配置在别的软件能连通。

**实测结论（curl 复现）**：服务端 HTTP 200、格式标准，问题全在 `llmService.testConnection`。
- `agnes-2.5-flash` 是**推理模型**：思维链写 `message.reasoning_content`，正文写 `message.content`，**`max_tokens` 同时约束两段**。
- 测试请求写死 `max_tokens: 5` → `reasoning_tokens: 5, text_tokens: 0`、`finish_reason: "length"` → `content` 是**空字符串**。
- `llmService.ts:68` 判定 `if (result.choices?.[0]?.message?.content)` → falsy → 误报「格式异常」。**去掉 max_tokens 后 content = "\n\nOk"，立即连通**。
- 排除项：鉴权头、端点拼接、API Key 均正确（`/v1/models` 正常返回 12 个模型）。

**同源问题（3 个，均未修）**：
1. 流式分支只读 `delta.content`，不读 `delta.reasoning_content`（实测先 14 个 reasoning chunk 再正文）→ 推理模型界面上长时间零输出。
2. 非流式解析同样不认 `reasoning_content`。
3. `finish_reason: "length"` 未翻译成可自诊断提示，笼统报「格式异常」误导排查。

**架构发现**：`ModelConfig.apiFormat`（`'openai'|'gemini'|'claude'`）是**死字段** —— `llmService` 无条件走 `/chat/completions`，UI 选 Gemini/Claude 零效果（假选择）。

### 实测数据（决定容错策略的关键依据，agnes 网关）

| 请求 | 结果 |
|---|---|
| `POST /v1/chat/completions` | 200 ✅ |
| `POST /chat/completions`（漏 /v1） | **403**，且返回体是 **Cloudflare 拦截 HTML**（不是 JSON 错误） |
| `POST /v1/nonexistent-endpoint`（路径真错） | **404**，返回 `{"error":{"message":"Invalid URL (POST /v1/nonexistent-endpoint)","type":"invalid_request_error"}}` |
| `POST /v1/chat/completions` + `Bearer sk-invalid` | **401** |
| `POST /v1/chat/completions/chat/completions`（重复拼接） | 200（该网关会忽略多余路径段，但别家会 404） |

**结论**：路径类失败 = **403/404**，鉴权失败 = **401**。所以「只在 403/404 上换候选重试」既安全（两者都不计费、也不会掩盖鉴权错误）又能救回「漏写 /v1」。

## 根因：第二个用户配置测不通 —— 是**渲染进程 CORS 预检被拒**（已改码，已验证）

**现象**：`https://token.sensenova.cn/v1` + `sensenova-6.8-flash-lite` 测试连接失败。用户贴的控制台报错：
`Access to fetch at '.../v1/chat/completions' from origin 'http://localhost:5173' has been blocked by CORS policy: Response to preflight request doesn't pass access control check: It does not have HTTP ok status.`

**排查过程（重要方法论）**：
1. curl 原样请求 → **HTTP 200、正文非空**（`content` 有值，`reasoning` 也有）。**说明服务端、鉴权、端点、模型全都对**，与上次 agnes 的「推理模型被 max_tokens 截断」完全不同。
2. 用 **Playwright + 真实 Chromium** 在 http 源上跑同样的 fetch：sensenova → `TypeError: Failed to fetch`；agnes → 200。**同时抓到控制台里的 CORS 原文**。
3. 对比两个端点的 **OPTIONS 预检**：agnes → `204` + `ACAO: *` + `ACAM: GET,POST,...` + `ACAH: *`；**sensenova → 所有路径（`/v1/chat/completions`、`/v1/models`、`/v1`）一律 `404` + 空 body、无任何 CORS 头**。
4. 结论：**该网关根本没实现 OPTIONS 预检**。而请求带 `Authorization` 头（非 CORS 安全列表头）→ 浏览器**必然**先发预检 → 预检非 2xx → 浏览器判定失败 → `fetch` 抛 `TypeError: Failed to fetch`。

**为什么以前没暴露**：之前用过的网关（agnes 等，多为 FastAPI/加了 CORS 中间件）会正确响应预检，所以渲染进程直连一直"碰巧"能用。sensenova 属于不做预检的那一类。**桌面软件（Cherry Studio 等）能连是因为它们从主进程/Node 发包，没有 Origin，不走 CORS。**

**用户的决定**：改成 **Node 侧（主进程）转发**。

## 第七轮：第三个配置测不通 —— 根因是**系统代理（Clash Verge）对该域名不通**（已定位，未改码）

**现象**：`https://api.mmkg.cloud/v1`（New API 中转网关，Cloudflare 前置）+ 该网关下的多个模型，测试连接报
`网络请求失败：无法建立连接。已自动重试 1 次仍失败。通道：主进程转发（不受 CORS 约束），请检查网络/代理能否到达该地址。原始错误：net::ERR_CONNECTION_CLOSED`。

**证据链（全部本机实测）**：

| 路径 | 结果 |
|---|---|
| curl 直连 | ✅ 401 / 0.39s，8/8 稳定（主机、DNS、TLS、路径、鉴权头全对）|
| curl `-x 127.0.0.1:7897` | ⚠️ 前 5 次 ✅（0.6–2.2s），后 3 次**瞬间失败**（0.001s，http=000）|
| Playwright 真实 Chromium（直连 / 显式代理 / 关 QUIC / 关 HTTP2+降 TLS / 关 ECH+DoH 共 7 种）| ✅ 全部 401 → 排除 Chromium 版本与协议栈 |
| **Electron 30.5.1（Chromium 124）经系统代理** | ❌ **`net::ERR_CONNECTION_CLOSED`，每次约 10.0s，3/3，复测 2/2** |
| **同一 Electron 强制直连（`session.fromPartition` + `setProxy({mode:'direct'})`）** | ✅ 401 / 385ms、203ms |
| Electron 经同一代理 → `token.sensenova.cn` | ✅ 401 / 162ms（代理本身是活的，只此域名走不通）|

**决定性证据**：`session.defaultSession.resolveProxy(url)` → **`PROXY 127.0.0.1:7897`**。注册表 `ProxyEnable=1` / `ProxyServer=127.0.0.1:7897` / `ProxyOverride` 含私网段与 `137.168.*`；进程 `clash-verge` + `verge-mihomo`（pid 23956，监听 7897）。**`net.fetch` 默认继承系统代理，而 curl 没有代理环境变量 → 直连。这就是「curl 通、应用不通」的全部原因。**

**关键教训**：**「curl 能通」不能证明应用能通** —— 两者可能根本不是同一条路。要判断通道，永远用 `resolveProxy()`，不要用 curl 推断。

**兜底机制已验证可行**（`electron.d.ts` 依据）：`session.fromPartition('llm-direct', { cache:false })` + `await setProxy({ mode:'direct' })` + `ses.fetch(...)`（`Session.fetch` 与 `net.fetch` 同签名）。`FromPartitionOptions` 只有 `cache`，**没有 proxy 字段**，必须 setProxy 且要 await。

**重大工具发现（推翻旧结论）**：本机**可以**跑 Electron 做真实网络验证 —— PowerShell 里 `Remove-Item env:ELECTRON_RUN_AS_NODE` 后用 `& $exe "D:\...\el-net-test" --no-sandbox`（目录含 package.json/main + 主进程 `app.whenReady()` → `net.fetch` → `fs.writeFileSync` 结果 → `app.exit(0)`）**能跑通并落地结果文件**。失败的两种写法：Bash 里 `env -u ELECTRON_RUN_AS_NODE ... electron.exe`（退出码 0、什么都不做）、`Start-Process -RedirectStandardOutput`。MEMORY.md 里「GUI 进程起不来、别验证」的旧条目已更正。

**未改任何代码**，等用户确认修复范围（自动兜底 / 每模型开关 / 只改提示）。

## 已落地：资产提示词回填「协议可配 + 多层容错」（用户诉求：不同模型返回格式不一致）
