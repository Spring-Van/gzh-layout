## 解析架构调研与方案设计（未改代码）

用户质疑「输出协议与解析被写死了」，连续三轮展开设计讨论 + 代码实地勘察。

**勘察结论**（已写入 MEMORY.md「模板类型 × 解析机制」）：
8 类模板中只有 `asset-prompt` / `extract` / `storyboard` 需要结构化解析，且三者范式完全不同。
只有 `asset-prompt` 是**闭集映射**（必须把 N 段匹配回 N 个预设状态）—— 这是它唯一会报「协议与解析不匹配」的根本原因；
`extract` / `storyboard` 是**开集生成**，位置即归属，本身相当健壮。

**发现的不一致**：`parseChineseAssetReport` 严格匹配 1/2/3 个 `#`，而 `PAGE_HEADER_RE` 用 `#{1,6}` 容忍任意层级 —— 同一项目两套标准。

**达成的设计方向（尚未实施）**：
1. 终态目标：一份「格式定义」同时编译出「协议文本（给模型）」+「解析规则（给引擎）」→ 结构上不可能失配，取代「协议与解析手工对齐」。
2. 用户自定义格式的接口应是**写期望样例**而非写规则：AI 从样例泛化规则 → 本地样例自验 → 用户试跑确认才保存。
3. 规则载体只做两档：结构模板（默认）+ 正则 DSL（高级，需 ReDoS 防护）；不做可视编排与沙箱执行。
4. 降级阶梯：自定义规则 → 内置 auto 管线 → 索引锚点 → AI 抽取（默认关闭）。
5. 实施顺序：① 抽共用**归一化层**（3 条链路共用、纯加法、可开关，收益最广）② asset-prompt 格式定义 + 样例推导 ③ 可选：extract/storyboard 接入层级提取器。
6. **明确不动** extract / storyboard 的现有解析器（历史兼容包袱 + 失败模式不同，改了风险大于收益）。

**待用户确认**：是否在 extract / storyboard 处实际遇到过解析失败（决定归一化层的覆盖范围）。

## 落地：统一输出协议为 Markdown（批量/逐条同格式）+ 取消解析方式档位

用户拍板：①「逐条生成也返回同样的输出格式，因为提示词模板的输出格式都是一样的，只是说只解析一个」；
②「协议文本可自由改会被改坏」用「在输出协议处提示输出格式为 Markdown」解决。本轮已实施。

**核心设计：输出协议拆两层，格式层不可覆盖**
- 【返回格式】= `OUTPUT_FORMAT_DEFAULTS[type]`（六环节统一 Markdown），由系统**恒在**注入、放在提示词最后（模型对靠后指令更敏感）；模板改不到 → 改不坏解析。
- 【内容要求】= 模板 `outputProtocol`，用户自由写，只追加、**不参与解析**；留空落到 `OUTPUT_CONTENT_DEFAULTS`（目前仅 asset-prompt 有）。
- asset-prompt 格式段 = `ASSET_PROMPT_FORMAT`（「【资产名｜状态名】+ 提示词正文」逐条）；内容要求默认 = `ASSET_PROMPT_CONTENT_REQUIREMENT`。

**逐条与批量同格式**
- `buildSingleAssetPrompt` 不再有独立逐条协议（原 `ASSET_PROMPT_PER_ITEM_PROTOCOL` 删除）。
- 新增 `extractSinglePromptText(content, ref)`（assetPromptParser）：单目标跑同一管线，命中取正文；未命中则剥掉行首包装 + 首行客套后退化为整段正文 —— 单条场景无错配风险，宁可原样收下也不要因格式细节丢结果。
- `rewriteAssetPrompt` 改走该函数（原先直接 `content.trim()`）。

**删除项**：`PromptOutputParser` 类型、`PromptTemplate.outputParser` 字段、`ASSET_PROMPT_PARSER_SPECS` / `outputParserOptions` / `getOutputParserSpec`、`protocolMode` 参数、`plain` / `sequential` 档、JSON/序号/顺序三套协议常量。
解析器**保留** JSON / 序号 / 顺序三层作为内部容错（模型自作主张时能救），但不再作为用户选项。
`AssetPromptParseStage` 增 `none`（全部形态都没识别出）；诊断去掉 `parser` 字段。
存量模板里的 `outputParser` 值被忽略，行为等同统一 Markdown 解析（只提示不改写）。

**UI**：设置页输出协议区 = 只读「返回格式（系统固定 · Markdown）」+ 可编辑「内容要求」；删掉「解析方式」下拉。

**校验**：vue-tsc 零报错；vitest 15 文件全绿（改 4 例：删档位用例、补单条回填用例、`【输出要求】` 断言改 `【返回格式】`、逐条协议断言改为同格式）。

## 再改版：删掉「输出协议」框，格式写进模板内容

用户拍板（两问的答复）：①「输出协议这个框删掉，只保留提示词内容输入框，全部提示词拼接按照提示词内容输入框的内容拼接；有输出格式解析的，需要在底部提示一行，按照 markdown 解析，不要过多解释」；
②「默认的提示词内容内直接含有输出格式，不再单独放在输出格式输出框了，所有提示词模板都这样改」。

**核实结论：真正需要解析的是 4 个环节**（用户列的 4 个里有一个不需要）
- 需要：`storyboard`（分镜生成 `parseStoryboardResponse` + 页面 AI 优化 `parsePanelBlock`）、`extract`（`parseAssetExtractionResponse`）、`asset-prompt` 批量·一次性（`parseAssetPromptResponse`）、`story`（旧版漫画项目编辑器，JSON）。
- 不需要：`analysis` / `script`（整段入库）、`panel-prompt`（**「批量生成分镜绘画提示词」是逐镜循环单次调用、返回纯文本，不解析**）、`style`（不调模型）。

**实施**
- `OUTPUT_FORMAT_DEFAULTS` → `OUTPUT_FORMAT_SPECS` + `outputFormatSpec(type)`；新增私有 `withFormatSpec()` 把格式说明**内联进推荐模板 content 末尾的【返回格式】段**（`RECOMMENDED_TEMPLATE_BASE` → `withFormatSpec` 映射生成导出的 `RECOMMENDED_TEMPLATES`）。
- 删除 `applyOutputProtocol` / `defaultOutputProtocol` / `defaultContentRequirement` / `OUTPUT_CONTENT_DEFAULTS` / `ASSET_PROMPT_CONTENT_REQUIREMENT`；`renderPromptTemplate` 去掉 `customProtocol`，只做变量替换。
- 删除 `PromptTemplate.outputProtocol` 字段 + 全部传参点（assetPromptService ×2、panelPromptService、LongProjectAssetWorkbench ×5、LongProjectStoryboardTab ×3、SettingsView ×2）。
- `storyboardService` 的页面优化提示词改用 `outputFormatSpec('storyboard')`（同一份格式文本，避免两处不一致）。
- 设置页 `TemplateEditorForm`：删掉整个协议区（只读返回格式块 + 内容要求 textarea + 填入推荐协议按钮）；底部按类型显示一行 `parseHint`（amber，`-700 dark:-300`），需要解析的四种类型才显示。
- extract 模板里「系统会自动处理输出结构」改为「请严格遵守下面【返回格式】约定的输出结构」。

**校验**：vue-tsc 零报错；vitest 158 例 / 15 文件全绿（重写输出协议 describe 为「返回格式写在模板内容里」6 例）；`vite build` **成功**（D:/gzh-build-check 出完整产物）。
