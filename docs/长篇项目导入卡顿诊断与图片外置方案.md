# 长篇项目「手动导入」卡顿诊断与图片外置方案

> 诊断时间：2026-10-05　　对象：长篇项目「手动导入漫画剧本 / 原文分析」

## 一、结论先说

**导入剧本只改几 KB 文本，却要重写 400 MB 主库、并来回搬运 188 MB 项目数据。**

根因不是导入逻辑，而是**项目里的图片以 base64 内联存储**：长篇项目 188.5 MB 数据中，图片占 **99.93%**（仅 51 张图）。任何一次写库——导入文档、改个章节名、自动保存——都要为这 51 张图付全款。

---

## 二、实测数据

### 2.1 主库体积（本机 `~/Library/Application Support/gzh-layout/`）

| 文件 | 体积 |
|---|---|
| `comic-gen.json` | **400.0 MB** |
| `comic-gen.json.bak` | 400 MB |
| `comic-settings.json` | 52 KB |

内联 base64 图片共 **142 张 = 399.5 MB**，占全库 **99.9%**。

### 2.2 各项目体积构成

| 项目 | 整体 | 说明 |
|---|---|---|
| 卡通漫画 | 58.9 MB | 含 `generatedImages` 21.2 MB、`pageRefImages` 32.0 MB |
| 公众号卡通漫画 | 36.9 MB | 同上 |
| **长篇** | **188.9 MB** | `longProjectData` 184.6 MB，其中内联图 **51 张** |
| 财经 | 95.4 MB | 含 `pageRefImages` 59.8 MB |

### 2.3 长篇项目里图片挂在哪些字段（都是纯 dataURL 字符串）

| 字段路径 | 张数 | 体积 |
|---|---|---|
| `longProjectData.storyboardRuns[].panels[].cells[].assetBindings[].referenceImageIds[]` | 30 | 90.6 MB |
| `longProjectData.panelArtworks[].generatedImageIds[]` | 4 | 34.8 MB |
| `longProjectData.panelArtworks[].selectedImageId` | 3 | 31.8 MB |
| `longProjectData.assets[].variants[].generatedImageIds[]` | 8 | 23.8 MB |

> 注意：这些字段名叫 `xxxIds`，实际存的是图片数据本体，不是 id。这是本次问题的结构性来源。

### 2.4 单次写库耗时（400 MB）

| 环节 | 耗时 | 来源 |
|---|---|---|
| `JSON.stringify(data, null, 2)` | ≈ 1.9 s | 按 09-27 实测 494 MB→2308 ms 折算 |
| 写 `.tmp` + `fsync` | ≈ 0.4 s | 同上折算 |
| 备份 `copyFileSync` | ≈ 0.2 s | 同上折算 |
| 回读校验 | 0 s | 09-27 已跳过（>`verifyMaxBytes` 8 MB） |
| **主进程合计** | **≈ 2.5 s** | 全程同步阻塞主进程 |

### 2.5 渲染层搬运开销（长篇项目 188.5 MB，本次实测）

```
JSON.stringify(长篇项目) = 842 ms  ->  188.5 MB        ← 一次 IPC 往返的量级
外置为短引用后          = 0 ms    ->  0.14 MB        ← 降 99.93%
```

`mutateLongProjectData` 每次执行都要：

1. `getProject` —— 把 188 MB 项目从主进程搬到渲染进程（克隆 + 传输 + 反序列化）
2. `mutate` —— 应用修改（本次改动就几 KB）
3. `saveProject` —— 把 188 MB 再搬回主进程，主进程再写 400 MB

**一次导入 ≈ 两次 188 MB 跨进程搬运 + 一次 400 MB 重写 ≈ 4~6 s**，且全程同步。

## 三、根因链

```
点击「确认导入」
  └─ applyManualImport
       ├─ (若原文有未保存改动) saveCurrentChapter → mutateLongProjectData  ┐
       └─ importDoc                              → mutateLongProjectData  ┘ 每个都付：
             getProject 188MB 搬运 → saveProject 188MB 回传 → 主进程 stringify 400MB + 落盘
```

导入改动的是 `chapterScripts` / `chapterAnalyses` 里的一条文档（几 KB），
写入的却是整个 400 MB 库。

## 四、本次已修复（止血，已生效）

| # | 改动 | 文件 | 效果 |
|---|---|---|---|
| 1 | 写库前不再无条件 `JSON.parse(JSON.stringify(...))` 全量深拷贝，改为「先原样提交，仅当 IPC 因 Proxy 拒绝克隆时才回退深克隆」 | `useLongProjectPersistence.ts` | 每次写库省掉一次 188 MB 序列化（≈0.8 s）；安全网不变 |
| 2 | 导入弹窗点「确认导入」后立即关闭，落库过程用常驻提示「正在导入原文分析/漫画剧本…」，结束后替换为「已导入」 | `LongProject.vue` | 不再"点了没反应"；防重入 |
| 3 | 漫画模块 `useToast` 四个方法透传 toast id | `composables/useToast.ts` | 支持「进行中 → 结果」替换式提示（向后兼容） |

**原文分析导入与剧本导入是否同一问题？是，且完全同一条链路**：两者共用 `ManualResultImportDialog` → `confirmManualImport` → `applyManualImport` → `runChapterDoc.importDoc`，只有 `kind` 不同（写入 `chapterAnalyses` / `chapterScripts`）。以上修复同时覆盖两者。

> 止血后仍剩 ≈4~5 s：主进程写 400 MB（2.5 s）+ 两次 188 MB 跨进程搬运。要真正"点一下就好"，必须做第五节的根治。

## 五、根治方案：项目图片外置（待确认）

### 5.1 核心思路

把项目数据里的 `data:image/...;base64,...` 写到磁盘文件，库里只留引用：

```
data:image/png;base64,iVBORw0KGgoAAAANSUhEUg...   (数 MB)
        ↓ 落盘为文件
app-image://comic/a3f91c6e8b2d.png                (几十字节)
```

主库 400 MB → ≈1 MB，长篇项目数据 188.5 MB → 0.14 MB。

### 5.2 基础设施已经就绪（不需要新造轮子）

| 能力 | 现状 |
|---|---|
| `app-image://` 协议 | `electron/main.ts:26` 已注册（`secure` / `standard` / `supportFetchAPI` / `corsEnabled`） |
| dataURL 落盘 | `ImageHistoryService.persistDataUrl()` 已实现（生图历史图就是这么存的） |
| 渲染层显示 | `toDisplayImageUrl()` 对 `app-image:` 前缀原样返回；`<img src>` 直接可用 |
| **发给图像模型** | `openaiImageService.urlToPngBlob()` 对非 data URL 走 `fetch(url)` → blob → base64，`app-image://` 已被协议支持 ✅ |

### 5.3 改动面

**主进程（核心，2 处）**

1. `main.ts` 的协议 handler 增加 `comic` host 分支 → 指向 `userData/comic-images/`
2. `ComicDatabaseService.saveProject()`：写盘前深度遍历，把 dataURL 按内容 hash 落盘、替换为 `app-image://comic/<hash>.<ext>`
3. 一次性迁移：首次启动若检测到主库内仍有 dataURL，执行同样的替换并重写一次主库

**渲染层（需适配的 3 个点，均已定位）**

| 位置 | 现状 | 需改为 |
|---|---|---|
| `openaiImageService.ts:73` | data URL 走 fetch | 已兼容 ✅ |
| `agnesImageService.ts:40` | `startsWith('data:') ? value : 'data:image/png;base64,'+value` | ❌ 会把 `app-image://` 错包成 base64 串 |
| `llmService.ts:496` | `if (!startsWith('data:')) continue` | ❌ 会把外置图过滤掉（多模态传图给 LLM） |
| `PageSync.vue:854/891` | 只识别 `data:image/` | ⚠️ 导出/转存路径需支持引用 |

### 5.4 风险评估

| 风险 | 等级 | 应对 |
|---|---|---|
| 一次性迁移 400 MB 数据 | **高** | 迁移前另存 `comic-gen.json.premigration`；失败可整文件回滚 |
| 上述 3 个渲染层消费点漏改 → 某条链路拿不到图 | 中 | 全部已定位并验证；改完用「生成参考图 / 多模态传图 / 导出」三条链路实测 |
| 公众号项目（`pageData`/`syncData` 内嵌图）上传微信链路 `useWechatUpload` 不认 `app-image://` | 中 | **建议阶段一先只做长篇（comic）项目**，公众号项目留到阶段二并单独适配 |
| 图片成为孤儿文件（删章节/分镜后文件残留） | 低 | 后续加 GC（按引用扫描清理），不影响正确性 |
| 库文件不再"自包含"（不能单独拷走） | 低 | 业务上无此需求 |

### 5.5 预期收益

| 指标 | 现在 | 外置后 |
|---|---|---|
| 主库文件 | 400 MB | ≈1 MB |
| 长篇项目数据 | 188.5 MB | 0.14 MB |
| 单次写库 | ≈2.5 s | ≈10 ms |
| 单次导入总耗时 | ≈4~6 s | **≈0.2 s** |
| 渲染进程内存峰值 | 秒级 +1.2 GB 量级 | 百 MB 级 |
| 图片显示 | 全量塞进 JS 堆 | 浏览器按需加载 |

### 5.6 建议执行顺序

1. **阶段一（建议先做）**：长篇 comic 项目图片外置 + 迁移 + 上述 3 点适配 → 覆盖你当前主诉的卡顿场景
2. **阶段二**：公众号项目图片外置（含微信上传链路适配）
3. **阶段三（可选）**：孤儿图片 GC
