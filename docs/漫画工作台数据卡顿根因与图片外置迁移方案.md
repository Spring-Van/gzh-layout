# 漫画工作台「一操作数据就卡顿」根因诊断与图片外置迁移方案

> 诊断时间：2026-10-05　　范围：长篇项目（`longProjectData`）下的全部写库操作
> 关联文档：`docs/长篇项目导入卡顿诊断与图片外置方案.md`（同一根因在「手动导入」场景的早期诊断，含 400 MB 时期的实测）
> 状态：**待确认，未动任何数据**

---

## 一、TL;DR

**卡的不是某个功能，而是「写库」这件事本身。**

长篇项目 **291.7 MB** 数据里 99.9% 是内联 base64 图片。任何一次写库——编辑一句提示词、删一张图、切一次选中项、自动保存——都走同一条路：

```
渲染层拿到全量 291 MB  →  改几 KB  →  塞回主进程  →  主进程 stringify 291 MB + 写盘
```

单次操作 ≈ **渲染进程冻结 2 s+**、**主进程阻塞 2 s+**。

所以「为什么这么多地方操作数据都会卡」的答案是：**这些地方共用同一条写库路径，代价与"+点了几下"无关，只与"项目里存了多少图片"有关。** 导入剧本、填充提示词、删图、改提示词，全部同源。

修法只有一条：**把图片从项目数据里搬出去，库里只留引用**。图片按**项目分目录、按来源（生成／上传／参考）分子目录**落到磁盘，库里的字段值从几 MB 的 base64 变成几十字节的 `app-image://` 引用。做完之后长篇项目数据 291.7 MB → 约 1 MB，单次写库从 ~4 s 降到几十毫秒，且**所有路径一起变快**。

## 三、根因链：一次「删一张图」到底发生了什么

以「资产生图工作台 → 删除一张生成图」为例（编辑提示词、分镜删图、填充提示词完全同构）：

```
用户点「确认删除」
 └─ LongProjectAssetWorkbench.removeAssetImage()
     └─ emit('update:asset', { assetId, variantId, patch })      ← 载荷只有几百字节
         └─ PanelGenAssetTab.updateAssetVariants([payload])
             └─ props.mutateLongProjectData(mutator)
                 │
                 ├─ ① await comicDb.getProject(projectId)        ← IPC 全量回传
                 │     主进程结构克隆 291 MB → 渲染进程反序列化 291 MB
                 │     渲染进程主线程占用 ≈ 0.9 s
                 │
                 ├─ ② mutator(draft)                             ← 真正的工作：几百微秒
                 │
                 ├─ ③ submitProject → comicDb.saveProject(next)  ← IPC 全量回传
                 │     渲染进程序列化 291 MB（≈1.6 s，主线程冻结）
                 │     主进程反序列化 291 MB（≈0.9 s）
                 │     主进程 JSON.stringify 291 MB（≈1.6 s）+ 写盘（≈0.3 s）
                 │
                 └─ ④ project.value = updated                    ← 整个对象换新
                       所有依赖 project 的 computed 全部失效重算
                       整棵组件树重渲染；所有 <img> 重新绑定
                       `toFastDisplayImageUrl` 的 blob 缓存 key 是 dataURL 字符串本体，
                       新对象里的 base64 是新字符串实例 → 逐条重算 hash（每张 3~11 MB）
```

**代价分布：** ①③ 的跨进程搬运 ≈ 渲染进程 2.5 s + 主进程 2.8 s；④ 的响应式风暴另计数百毫秒。**用户感知的「卡顿」主要是 ①③④ 落在渲染主线程上。**

## 四、为什么之前做的「同 tick 攒批」不够

`useLongProjectPersistence.mutateLongProjectData` 已经做了两件事：

1. **同 tick 攒批**：把同一轮事件循环里的多个 mutator 合并成一次写库。→ 解决的是**次数**。
2. **省深克隆**：不再无条件 `JSON.parse(JSON.stringify())`。→ 省掉一次 291 MB 序列化。

但**单次写库要搬运 291 MB 这件事没变**。所以：

| 操作 | 攒批前 | 攒批后 | 用户感受 |
|---|---|---|---|
| 填充 10 条提示词 | 10 次搬运 | 1 次搬运 | 从"卡死几十秒"变成"卡 4 秒" |
| **删 1 张图 / 存 1 条提示词** | 1 次搬运 | 1 次搬运（无从合并） | **仍然卡 4 秒** |

这就是为什么「明明已经优化过，细碎操作还是卡」——**攒批对单次操作天然无效**。

## 五、方案：项目图片外置

### 5.1 目标形态：按项目分目录

```
data:image/png;base64,iVBORw0KGgoAAAANSUhEUgAA...      （3~11 MB）
        ↓ 按内容 hash 落盘
app-image://comic/咖啡店日常__8f3a2b/generated/a3f91c6e8b2d5f07.png   （约 60 字节）
```

磁盘布局（`userData/comic-images/`）：

```
comic-images/
  咖啡店日常__8f3a2b/                ← <项目名 sanitize>__<项目 id 前 6 位>
    generated/  a3f91c6e8b2d5f07.png   ← generatedImageIds / selectedImageId(s)
    uploaded/   7b2c9d1e4f0a8b32.png   ← uploadedImageIds
    reference/  4e5f6a7b1c2d3e40.png   ← referenceImageIds / sharedBlocks.referenceImages
  另一部漫画__c1d2e3/
    …
```

**为什么是这个形状（已与用户确认）**

| 决策 | 选择 | 理由 |
|---|---|---|
| 是否按项目分目录 | **分** | 能按项目定位；**删除项目 = 删除目录**，孤儿回收天然解决 |
| 是否按来源分类 | **分三类** | 遍历时字段名天然带来源信息，零额外元数据；一眼分清「AI 生成」与「我上传的」 |
| 目录名 | `<项目名>__<id 前6位>` | 人可读 + 唯一。不用纯 uuid（翻目录认不出），也不用纯项目名（重名冲突） |
| 文件名 | 内容 sha1 + 扩展名 | 稳定、可去重。**不做语义化文件名**（改名传染、旧文件成孤儿） |
| `index.json` | **不做** | 保持目录精简 |
| 去重范围 | **项目内** | 同一图在成图／绑定／参考之间共享一份；跨项目各存一份（可接受） |
| 导出下载 | **不动** | 内部缓存（hash 名、可被 GC）与用户导出（语义文件名、用户自选目录）是两套，不混用 |

> 「用户点下载」走 `downloadService` → 另存／打包 ZIP 到用户目录，**与外置目录无关**。外置目录里的文件可能被 GC 回收，用户导出的文件不会——所以它们必须分开。

**两个必须配套处理的点：**

1. **项目重命名**（目录名含项目名）。写库时比对 `sanitize(project.name)+'__'+id.slice(0,6)` 与现有引用中的目录名：
   - 一致 → 无操作
   - 不一致 → **先 `rename` 目录**，成功后再把项目内所有 `app-image://comic/<旧目录>/` 前缀替换为新名（同一次遍历顺手完成，零额外成本）
   - `rename` 失败 → 保持旧名、引用不动（宁可名字旧，不可改出断链）

2. **删除项目**。`deleteProjectCascade()` 中，**库记录删除成功之后**才 `rm -rf` 对应目录。顺序不能反——先删文件再删记录，一旦记录删失败就是「项目还在、图全没了」。目录删除失败只记日志（残留文件无害）。

**项目内去重怎么做**：遍历时维护 `Map<sha1, url>`，先用**已存在的 `app-image://comic/…` 引用**反向填充映射（保证幂等），遇到 `data:` 时算 sha1 → 命中即复用已有 URL，未命中才按当前字段判定 kind 落盘。同一张图同时出现在 `generatedImageIds` 与 `referenceImageIds` 时只落一份，归哪一类由首次遇到决定（纯目录归类，不影响功能）。

**字段 → kind 对照（遍历依据）**

| kind | 字段 |
|---|---|
| `generated` | `panelArtworks[].generatedImageIds[]` / `.selectedImageId`；`assets[].variants[].generatedImageIds[]`；绑定 `selectedImageIds[]` |
| `uploaded` | `assets[].variants[].uploadedImageIds[]` |
| `reference` | `assets[].variants[].referenceImageIds[]`；绑定 `referenceImageIds[]`；`assetGenConfig.sharedBlocks[].referenceImages[]`；`imageGenConfig.sharedBlocks[].referenceImages[]` |

### 5.2 数据流：改造前 vs 改造后

| 环节 | 改造前 | 改造后 |
|---|---|---|
| 加载项目 | IPC 291 MB + 反序列化 0.9 s | IPC ≈1 MB，**毫秒级** |
| 写库 | 渲染层序列化 291 MB + 主进程 stringify 291 MB | 各 ≈1 MB，**毫秒级** |
| 落库后重渲染 | blob 缓存 key 是 3~11 MB 字符串，逐条重算 hash | key 是短 URL，缓存稳定命中 |
| 图片显示 | 全量 base64 进 JS 堆 | 浏览器按 URL 按需从磁盘加载 |
| 渲染进程内存 | 峰值 GB 级 | 百 MB 级 |

### 5.3 基础设施现状：**不需要新造轮子**

| 能力 | 现状 |
|---|---|
| `app-image://` 协议 | `electron/main.ts:26` 已注册（`secure` / `standard` / `supportFetchAPI` / `corsEnabled`），handler 已支持 `history` / `local` 两个 host。⚠️ **但现只认单层文件名**：`resolveImagePath` 里 `filename !== path.basename(filename)` 直接拒绝（防目录穿越）。要支持 `<项目目录>/<kind>/<文件>` 三级，这里必须改，且**安全校验不能只是放开**（见 §5.7） |
| dataURL 落盘 | `ImageHistoryService.persistDataUrl()` **已实现**（生图历史图就是这么存的），但它是 `private` 且只按 `<stem>.<ext>` 单层落盘，需另写支持项目目录与 kind 的版本 |
| 渲染层显示 | `toDisplayImageUrl()` 对 `app-image:` 前缀原样返回；`toFastDisplayImageUrl()` 对非 `data:` 直接回落前者 → **现有 `<img>` 全部零改动可用** |
| 图片取用（fetch 路径） | `openaiImageService.urlToPngBlob()` 对非 data URL 走 `fetch(url)` → blob → base64，`app-image://` 被协议支持 ✅ |

### 5.4 关键设计 1：**写库必须返回外置后的项目**（这一步决定成败）

只在主进程写盘时替换是不够的——渲染层内存里仍然是 291 MB 的 base64，下一次操作照样卡。

```
主进程 saveProject(project)
  ├─ 深度遍历 longProjectData / imageGenConfig，把 dataURL 落盘替换为 app-image://
  ├─ 写盘（此时体积已 ≈1 MB）
  └─ return { success: true, project: 外置后的 project }   ← 新增返回值
       ↓
渲染层 submitProject 用返回值赋给 project.value
  → 渲染层内存同步瘦身到 ≈1 MB
  → 此后每一次 getProject / saveProject 都是小包
```

- **首次**写库仍要搬一次 291 MB（一次性），之后全部毫秒级。
- 新生成的图（dataURL，几 MB）在下次写库时被外置，随后内存也跟着变短——单次多几 MB 可接受。
- ⚠️ `comic:db:saveProject` 目前的返回值是 `{ success: true }`，必须扩展到携带 `project`。

### 5.5 关键设计 2：参考图输入归一化（**本次新发现的高危点**）

`assets[].variants[].referenceImageIds`、绑定 `referenceImageIds`、「共用属性」`referenceImages` 都是**要发给图像模型**的输入图。它们在下列路径里被**原样塞进请求体**：

| 服务 | 输入参考图去向 | 外置后会怎样 |
|---|---|---|
| `grsaiService.generate` | `{ images }` 原样进 JSON body | ❌ 第三方拿到 `app-image://…`，取不到图 |
| `duomiService.createTask` | `{ image }` 原样进 JSON body | ❌ 同上 |
| `agnesImageService.generate` | `extra_body.image` 原样进 body | ❌ 同上 |
| `openaiImageService`（兼容模式） | `images` 进 generations JSON body | ❌ 同上 |
| `openaiImageService`（标准模式 multipart） | `urlToPngBlob(url)` → `fetch(url)` | ✅ 已兼容 |

> ⚠️ 早期文档把 `agnesImageService.ts:40` 的 `b64ToDataUrl` 列为"需适配点"是**误判**——那行处理的是**模型返回的** `b64_json`，与输入参考图无关。真正的问题在输入侧，且四个服务都有。

**统一修法：** 新增一个渲染层共用的归一化函数

```ts
// src/shared/image/imageUrl.ts
/** 把项目内的图片引用解析成"可直接发给第三方"的形式（dataURL / http）。 */
export async function resolveModelInputImage(url: string): Promise<string>
// data: / http: / https: → 原样返回
// app-image:// → fetch(url) → blob → FileReader → dataURL
```

在 `imageGenerationService.generateWithModel` 的**入口处**对 `imageUrls` 统一 map 一次即可，四个服务不必各改。

### 5.6 关键设计 3：一次性迁移

在 `ComicDatabaseService.init()` 里做一次（**幂等**）：

```
if (检测到 this.data 的任一项目 longProjectData 内仍有 data:image/*;base64) {
   1. 把 comic-gen.json 复制为 comic-gen.json.premigration.json   ← 回滚锚点（已存在则不覆盖）
   2. 遍历外置（复用 5.4 的同一函数）
   3. 立即写盘一次
   4. console.log 迁移统计（张数 / 释放体积 / 耗时）
}
```

- 迁移只在启动时做一次，此后条件不成立直接跳过。
- 备份文件**不自动删除**，由用户确认无异常后自行清理。

### 5.7 关键设计 4：协议路径安全边界

`app-image://comic/<目录>/<kind>/<文件名>` 这个路径是从库数据里来的，而库数据可能被用户手改（导出的 JSON 可编辑后再导入）。**必须当作不可信输入**：

```
三段解析（任一段不合法 → 404）
  ① 目录   长度 ≤120、不含 `/` `\`、不含 `..`、sanitize 后非空   ← 项目名可能含中文/空格/emoji
  ② kind   ∈ { generated, uploaded, reference }                  ← 白名单
  ③ 文件名 /^[a-f0-9]{40}\.(png|jpg|jpeg|webp|gif|avif)$/         ← sha1 + 扩展名白名单
→ path.normalize(path.join(root, 目录, kind, 文件名))
→ 断言 resolved.startsWith(root + path.sep)                       ← 兜底，任何一段作弊都被挡住
```

- **kind 与文件名走白名单**（"只允许合法字符"，而不是"排除危险字符"）
- **目录名无法白名单**（项目名任意），靠 sanitize + `..` 检查 + 最后 `startsWith(root)` 兜底
- 失败一律 404，与现有 handler 行为一致
- 现有 `history` / `local` 两个分支**保持不动**（`local` 分支要 `path.isAbsolute` 才放行，本就与 `comic` 无关）

**方案之外、实施中发现的必要补充：**

1. **写库后要刷新「长期存活的本地状态」**（方案没覆盖）。`ImageConfigDrawer.autoSaveConfig` 与 `LongProjectStoryboardTab.handleSaveImageConfig` 都用本地 ref 持有 `imageGenConfig`，不把返回值写回去，内存里就一直压着参考图 base64，下一次保存照样搬运 —— 外置收益会被吃掉。
2. **目录名清洗的正则必须带 `g`**。`replace()` 无 `g` 时只替换第一个匹配字符：`a/b\c:d` 只会清掉 `/`，剩下的 `\` 仍构成路径分隔 → 目录逃逸。同时 `test()` 不能用带 `g` 的实例（`lastIndex` 会跨调用残留）。
3. **`removeProjectDirByProjectId` 不能借道 `buildProjectDirName` 取尾串**：后者用项目名占位、长度不定，取尾 6 位会算错；改为直接用项目 id 过滤非字母数字后取前 6 位。

**与方案的差异：** 备份文件名统一为 `comic-gen.json.premigration.json`（与既有 `.bak` 风格一致，且已存在时不覆盖，保留最早那份纯内联原库）；§六 的 10 处里 `preload.ts` 实际无需改动（本来就是 `any` 透传）。

**仍待实机验收**：见 §九 —— 其中四条生图链路（资产单张 / 资产批量 / 分镜有绑定 / 分镜无绑定）必须实测，归一化漏改会让模型**静默丢参考图**。

> （迁移后库本身已不含图片，单独拷库等于丢图）。本节保留仅作历史记录。

```
1. 退出应用（确保没有写盘在途）
2. rm -rf  ~/Library/Application Support/gzh-layout/comic-images/          # 清掉外置产物
3. mv     ~/Library/Application Support/gzh-layout/comic-gen.json.premigration.json \
          ~/Library/Application Support/gzh-layout/comic-gen.json          # 还原原库
4. （若有）还原 comic-gen.json.bak
5. 重新启动，确认项目数据与图片完好
```

## 十一、遗留问题

1. **`getAllProjects()` 仍会把含 base64 的全量项目经 IPC 交给渲染层**（项目首页 / 素材库调用）。阶段一之后公众号项目仍是 191 MB，该接口需要改成"只返回摘要"。
2. **写放大仍然存在**：只要还有一次操作触发全量 stringify，主进程就会阻塞。阶段一之后长篇项目已不是瓶颈，公众号项目仍是。
3. **`mutateLongProjectData` 的写前 `getProject`** 在多页面（主页面 / 生图工作台）场景下承担"合并其他页面写入"的职责。外置后它变便宜（≈1 MB），可保留不动；若后续要再压，可考虑主进程侧 RMW + 小包 patch。
4. **项目内孤儿图片**：删单张生成图／上传图后，磁盘文件保留（同一 sha1 可能仍被绑定的 `referenceImageIds` 引用）。精确判定需全项目扫引用，属阶段三 GC。
