# 本地存储性能诊断与根治方案

> 起因：系统设置里任意一个配置点保存都会卡顿，甚至看起来「点了保存却没保存上」；单张图「单独生成」点击后也要等几秒才出现 loading。二者同一个根因。

## 一、实测数据

本机 `userData/comic-gen.json`（macOS：`~/Library/Application Support/gzh-layout/`）：

| 指标 | 数值 |
| --- | --- |
| 库文件体积 | 494.2 MB（备份 `.bak` 另占 ≈480 MB） |
| `projects` 分区 | 473.9 MB（95.9%） |
| `projectAssets` | 14.3 MB |
| `materials` | 5.9 MB |
| `modelConfigs` + `promptTemplates` + `appSettings` | ≈ 0 MB（几 KB） |
| 内联 base64 图片 | 173 张（png 168 / jpeg 5），占 493.5 MB，即 **99.9%** |

单次保存（写任意一个字段都要付的代价）：

| 步骤 | 耗时 | 性质 |
| --- | --- | --- |
| `JSON.stringify(库, null, 2)` | 2308 ms | CPU，同步阻塞 |
| 写 `.tmp` + `fsync` | 515 ms | 同步 IO |
| 回读 `.tmp` 并 `JSON.parse` 校验 | 1482 ms | 纯浪费 |
| 备份 `copyFileSync(旧主文件)` | 237 ms | 同步 IO |
| **合计** | **≈ 4560 ms** | 全程阻塞主进程 |

附：`JSON.parse` 494 MB 实测 `heapUsed` 达到 **1486 MB**。一次保存额外解析一份临时文件，相当于在 16 GB 机器上再申请 1.5 GB 堆，这是「点保存后长时间毫无反应、甚至以为没保存上」的直接来源。

## 二、根因

**单一 JSON 文件 + 全量重写。**

任何一次写操作（保存系统设置、切换模型、单个项目自动保存、写一张图…）都会把整个 494 MB 的库重新序列化、写盘、回读校验、复制备份一遍。设置数据只占 1 KB，却要陪跑 494 MB —— 这就是「系统内为什么到处都是这种卡顿」的唯一解释。

## 三、本次已修复

1. **拆分存储**：`modelConfigs` / `promptTemplates` / `appSettings` 拆到独立的 `userData/comic-settings.json`，与项目主库彻底解耦。
   - 系统设置的保存只序列化几 KB。
   - 旧版单文件库首次启动自动迁移（密钥密文随迁，项目数据原封不动）。
   - 对外 IPC / 渲染层接口完全不变。
2. **`JsonFileStore` 大文件跳过回读校验**（`verifyMaxBytes`，默认 8 MB）：省下 1482 ms，并消除额外 1.5 GB 内存峰值。原子替换 + `.bak` 仍然是安全网；小文件保持原有校验强度。
3. **保存失败不再静默**：系统设置的写库动作统一走错误捕获，写盘失败（磁盘满、系统密钥服务不可用等）会弹错误提示。此前这类失败是静默的 —— 界面上毫无反应，用户只能看到「没保存上」。

效果对比：

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| 保存提示词模板 / 模型 / 公众号设置 | ≈ 4.5 s 主进程冻结 | < 20 ms |
| 项目类写盘（生图结果、分镜、自动保存） | ≈ 4.5 s | ≈ 2.8 s |

## 四、仍未根治：项目主库依旧 494 MB

项目主库每次写入仍需 ≈ 2.8 s，因为 **99.9% 的体积是 173 张内联 base64 图片**。三个候选方案：

### 方案 A：图片外置为磁盘文件 + `app-image://` 引用（推荐）

系统里已经有一套现成机制：`electron/services/image-history.service.ts` 的 `persistDataUrl()` 会把 `data:image/png;base64,...` 落盘成 `userData/image-studio/images/<name>.png`，库里只留 `app-image://history/<name>.png`，渲染层 `<img>` 原样显示即可（`electron/main.ts` 已注册协议）。

做法：项目数据写库前，把 `coverImage` / `generatedImages` / 工件图等字段里的 dataURL 落盘成 `userData/comic-images/<hash>.png`，库中只存引用。

- 收益：主库 494 MB → ≈ 1 MB，**所有**项目写操作进入毫秒级；`getAllProjects()` 的 IPC 传输也不再搬 494 MB。
- 代价：需一次性迁移 173 张图；上传公众号、生图参考图等链路需要把引用还原为绝对路径或 base64（`resolveImagePath` 可复用）；触及图片读写的每一处，改动面最广。
- 风险：中高，需要真机全链路回归（生图 / 参考图 / 导出 / 同步公众号）。

### 方案 B：项目分片 + 列表摘要

每个项目一个文件（`projects/<id>.json`），列表接口只返回 `id/name/cover/updatedAt` 摘要，打开项目时才读全量。

- 收益：编辑一个项目不再重写其它项目；IPC 列表不再传 494 MB。
- 局限：单个大项目自身仍可能几百 MB，卡顿只是被推迟。

### 方案 C：写盘异步化 + 写入合并

保持数据结构不变，把落盘移到后台（异步 IO + 短窗口合并多次写入），IPC 立即返回。

- 收益：UI 立刻响应，改动最小。
- 代价：需在退出前 flush，异常退出可能丢最后几百毫秒；CPU / IO 总量不变，只是不阻塞界面。

### 建议顺序

先做 **A**（真正根治，且基础设施已存在），若想先要小改动可叠加 **C** 作为兜底；B 可作为 A 的补充（两者不冲突）。
